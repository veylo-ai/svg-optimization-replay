When SVG optimization erases a drawing

A print-only hiding rule should leave this red rectangle visible on screen. In one synthetic test, the hosted SVGOMG optimizer returned an SVG with no drawing elements.

This page replays saved inputs and captured outputs. It does not run an optimizer. The tested app identified itself as SVGO v4.0.0; its settings were left as found in the browser session.

1. A style with a media="print" attribute

2. A control with an explicit @media print wrapper

Changing only the style representation retained the drawing in the observed output. That is a result for this fixture; the print comparison below distinguishes direct SVG documents from embedded images. Arbitrary artwork remains untested.

3. Two settings must change in this fixture

A follow-up in the same hosted app tested all four combinations of Merge styles and Inline styles, with other settings left as found. Turning either one off alone still removed the drawing. Turning both off retained the drawing and its print-scoped style in this particular output.

This is a possible setting combination to test on this fixture, not a general repair. The print comparison below covers these saved strings in Chromium only. Settings can affect other artwork; compare your required renders.

4. Printing depends on how the SVG is used

In an October 27 follow-up using the same eight saved strings, Chromium 156.0.8078.47 produced different PDF output for direct SVG documents and HTML image elements. The four retained drawings had 10,000 red pixels on screen. In generated PDFs they kept those pixels when embedded as <img> images, but had zero when opened directly as SVG documents. The four already empty outputs had zero in both routes.

For this direct-document route, the wrapper pair and both-settings-off output preserved the original’s intended print hiding. The image route printed the retained drawings. These are observed results for these strings and routes; test the context your own artwork uses.
